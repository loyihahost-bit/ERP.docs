# AI Offline and Synchronization Architecture

**Document ID:** AI-20
**Status:** Proposed
**Version:** 1.0
**Scope:** FastFood ERP
**Parent Document:** `docs/04_Architecture/07_AI/README.md`

## 1. Purpose

This document defines how AI functionality behaves when FastFood ERP operates offline or when connectivity between the frontend, Backend and AI infrastructure is temporarily unavailable.

The primary objective is to preserve:

* ERP operational continuity;
* transaction integrity;
* Business and Branch isolation;
* AI result integrity;
* synchronization consistency;
* authorization;
* subscription enforcement;
* historical integrity;
* predictable recovery.

AI must never weaken the existing Offline-First architecture.

The core principle is:

> Offline AI may preserve previously authorized knowledge and queue permitted requests, but it must never become an alternative source of authoritative ERP state.

---

## 3. Core Principle

The ERP remains authoritative.

AI remains assistive.

Offline mode does not change this relationship.

```text
Authoritative ERP State
        ↓
Server
        ↓
AI Input / AI Processing
        ↓
AI Result
        ↓
Frontend Cache / Offline State
```

The offline client must never become authoritative merely because the server is temporarily unavailable.

---

## 4. Offline AI Capability Model

AI functionality is divided into three categories:

1. Offline-readable AI data
2. Queueable AI requests
3. Server-required AI operations

The frontend must know which category applies to each AI capability.

---

## 5. Offline-Readable AI Data

The client may display previously synchronized AI results when permitted.

Examples:

* latest demand forecast;
* previous inventory recommendation;
* historical anomaly;
* previous business insight;
* completed AI report explanation.

Such data must include:

* generation timestamp;
* Business;
* Branch where applicable;
* period;
* model/pipeline version where relevant;
* freshness information;
* synchronization state.

---

## 6. Offline-Readable Result Example

```text
AI Forecast

Generated:
Today 09:20

Branch:
Chilanzar

Forecast:
1,300–1,400 units

Status:
Cached / Offline

Data may be outdated.
```

The frontend must clearly identify that the result is not necessarily current.

---

## 7. Offline AI Request Classification

Before a request is queued or executed offline, the system classifies it as:

```text
OFFLINE_READ
OFFLINE_QUEUEABLE
SERVER_REQUIRED
NOT_ALLOWED_OFFLINE
```

Examples:

| Operation                       | Offline                           |
| ------------------------------- | --------------------------------- |
| View previously synced forecast | Allowed                           |
| View previous recommendation    | Allowed                           |
| View historical AI insight      | Allowed                           |
| Generate new server forecast    | Queueable if explicitly supported |
| LLM assistant using server data | Usually unavailable               |
| Change Product price using AI   | Not allowed                       |
| Modify inventory using AI       | Not allowed                       |
| Change payroll using AI         | Not allowed                       |
| Change permissions using AI     | Not allowed                       |

---

## 8. Offline AI Is Not Local Authority

The client may calculate temporary UI state, but such calculations do not become authoritative ERP or AI results.

For example:

```text
Offline device
   ↓
Local calculation
   ↓
Temporary suggestion
```

must not be represented as:

```text
Server-approved AI prediction
```

unless it was generated by an explicitly approved local inference capability.

---

## 9. Local Inference

Local AI inference may be introduced only when explicitly approved by the AI architecture.

If local inference is enabled:

* the model must be approved;
* model version must be known;
* model artifact integrity must be verified;
* supported inputs must be defined;
* Business/Branch scope must remain enforced;
* result must be marked as local/offline;
* result must not automatically become authoritative.

---

## 10. Default Local Inference Policy

The default architecture does not require local AI inference.

Server-side AI remains the primary execution environment.

This avoids:

* large browser model requirements;
* excessive device CPU/RAM usage;
* inconsistent model versions;
* difficult model security;
* unpredictable POS performance.

---

## 11. Offline AI Cache

AI results may be cached locally when required for operational continuity.

Cache entries should contain:

* result UUID;
* Business UUID;
* Branch UUID where applicable;
* AI capability;
* model UUID/version where applicable;
* pipeline version where applicable;
* generation timestamp;
* source period;
* freshness metadata;
* synchronization timestamp;
* expiration policy;
* result status.

---

## 12. Cache Authority

The local AI cache is:

**non-authoritative.**

The cache must never override:

* ERP database state;
* server configuration;
* server authorization;
* subscription state;
* current menu;
* current pricing;
* inventory ledger;
* payroll;
* cash state.

---

## 13. Cache Isolation

Every cached AI result must be isolated by Business.

Branch-scoped results must additionally be isolated by Branch.

A cache lookup must not return another Business's result.

Cache keys should include sufficient scope information, for example:

```text
Business UUID
Branch UUID
AI Capability
Model Version
Pipeline Version
Period
Result Type
```

---

## 14. Cache Invalidation

AI cache invalidation may occur because of:

* newer server result;
* model version change;
* pipeline version change;
* Business state change;
* Branch configuration change;
* authorization change;
* subscription restriction;
* result expiration;
* security event;
* data deletion.

Invalidation must be explicit rather than relying only on browser memory.

---

## 15. Stale AI Data

Offline AI results can become stale.

The frontend must display stale state when freshness affects interpretation.

Possible states:

```text
CURRENT
RECENT
STALE
EXPIRED
INVALIDATED
```

An expired result must not be presented as a current recommendation.

---

## 16. Stale Forecast

Example:

```text
Demand Forecast

Generated:
Yesterday 09:00

Status:
Stale

The forecast may no longer reflect
current inventory and sales.
```

The user may still inspect the result if retention policy allows it.

---

## 17. Offline ERP Transactions as AI Inputs

Offline ERP transactions may later become AI inputs after synchronization.

For example:

```text
Offline Order
    ↓
Local transaction
    ↓
Server synchronization
    ↓
Server validation
    ↓
Authoritative ERP state
    ↓
AI pipeline
```

AI must not treat an unvalidated offline transaction as authoritative.

---

## 18. Transaction Synchronization Priority

ERP transaction synchronization has priority over AI configuration or AI result synchronization.

Example:

```text
Offline Order
     ↓
Sync Order
     ↓
Server validates Order
     ↓
Inventory / Payment state updated
     ↓
AI data refresh
```

This prevents AI from generating recommendations from incomplete authoritative state.

---

## 19. AI Configuration Synchronization

AI configuration includes, where applicable:

* enabled capabilities;
* model selection;
* feature configuration;
* forecast configuration;
* recommendation configuration;
* refresh intervals;
* UI feature configuration.

Configuration synchronization must use versioned server state.

---

## 20. Configuration Authority

The server is authoritative for AI configuration.

Offline devices may use the latest valid configuration known to them.

They must not assume that their local configuration remains current indefinitely.

---

## 21. AI Configuration Version

Each relevant AI configuration should be associated with:

* configuration UUID;
* Business UUID;
* Branch UUID where applicable;
* version;
* creation timestamp;
* effective timestamp;
* status;
* source;
* actor where applicable.

The frontend should retain the version used to produce a local AI request or result.

---

## 22. Configuration Synchronization Flow

```text
Local Configuration Version A
          ↓
Device reconnects
          ↓
Server Configuration Version B
          ↓
Version comparison
          ↓
Update local configuration
          ↓
Invalidate incompatible local AI state
```

The client must not silently merge incompatible configurations.

---

## 23. AI Request Queue

When a supported AI operation is queueable offline, the frontend may create a local pending request.

The local request must contain:

* operation UUID;
* Business UUID;
* Branch UUID where applicable;
* employee/session context;
* capability;
* request payload;
* creation timestamp;
* local configuration version;
* client device UUID;
* status.

---

## 24. Queue States

Offline AI requests may use:

```text
PENDING
SYNCING
ACCEPTED
RUNNING
SUCCEEDED
RETRY_PENDING
FAILED
CANCELLED
REJECTED
EXPIRED
CONFLICT
```

The frontend must distinguish local queue state from server AI job state.

---

## 25. Queue Does Not Mean Success

Creating a local offline AI request does not mean the server accepted it.

Example:

```text
Queued offline
```

must not be shown as:

```text
AI generation started
```

until the server confirms acceptance.

---

## 26. Reconnection Flow

When connectivity returns:

```text
Network restored
      ↓
Authenticate / validate session
      ↓
Validate Business state
      ↓
Validate subscription
      ↓
Sync ERP transactions
      ↓
Sync configuration
      ↓
Submit eligible AI requests
      ↓
Receive AI job/result
      ↓
Update local state
```

The exact implementation may optimize these stages, but authorization and authoritative state validation remain mandatory.

---

## 27. Revalidation on Synchronization

Every queued AI request must be revalidated when it reaches the server.

Validation includes:

* Business existence;
* Business lifecycle state;
* Branch existence;
* employee status;
* authorization;
* permission;
* subscription entitlement;
* AI capability;
* request validity;
* configuration compatibility;
* model availability where relevant.

---

## 28. Subscription Revalidation

A queued offline AI request must not bypass subscription restrictions.

Example:

```text
AI request created while subscription ACTIVE
             ↓
Subscription expires
             ↓
Device reconnects
             ↓
Server rejects modifying AI operation
```

The device must not assume that prior authorization remains valid forever.

---

## 29. Business Lifecycle Revalidation

The server must reject queued AI operations when the Business is no longer operationally eligible.

Examples:

* READ_ONLY;
* DELETION_ELIGIBLE;
* DELETING;
* DELETED.

A queued request must not resurrect a deleted or expired Business.

---

## 30. Employee Revalidation

The employee associated with an offline AI request may become inactive before synchronization.

The server must revalidate employee status.

An inactive employee must not gain new AI permissions merely because the request was created earlier.

---

## 31. Permission Revalidation

Offline requests do not permanently preserve authorization.

A request created when an employee had permission may be rejected if the permission was revoked before synchronization.

This prevents stale authorization from becoming a security bypass.

---

## 32. Branch Scope Revalidation

The server must verify that:

* Business matches;
* Branch belongs to Business;
* employee can access Branch;
* AI capability allows the requested Branch scope.

A request containing an invalid Branch UUID must be rejected.

---

## 33. Configuration Version Conflict

A queued request may reference configuration version A while the server now uses version B.

The system must determine whether the request remains valid.

Possible outcomes:

```text
Compatible
→ Accept

Incompatible
→ Conflict / Rebuild / Reject
```

The system must not silently reinterpret the request using a materially different configuration.

---

## 34. Model Version Conflict

An offline request may reference Model Version A while the server has Model Version B active.

The system may:

* execute against the originally approved model if still supported;
* re-evaluate using the current approved model;
* reject and require regeneration.

The selected policy must be deterministic and recorded.

---

## 35. AI Result Synchronization

Completed AI results may synchronize from server to device.

Synchronization must preserve:

* result UUID;
* generation timestamp;
* model version;
* pipeline version;
* Business/Branch scope;
* source period;
* result status;
* provenance;
* freshness.

The local copy must not alter the original result.

---

## 36. Result Immutability

Once an AI result is generated and persisted as an immutable result:

* the result must not be silently rewritten;
* corrections create a new result/version;
* newer results supersede older results according to defined resolution rules.

Historical AI results remain traceable.

---

## 37. Prediction Synchronization

Prediction synchronization must preserve the difference between:

* prediction;
* actual outcome;
* later evaluation.

For example:

```text
Prediction P1
Generated Monday
Expected Tuesday demand

Later:
Actual Tuesday demand

Evaluation:
Prediction error = ...
```

The actual ERP result must never be replaced by the prediction.

---

## 38. Recommendation Synchronization

Offline recommendations must preserve:

* recommendation UUID;
* creation time;
* scope;
* recommendation version;
* source data version;
* status.

A recommendation may become:

```text
ACTIVE
EXPIRED
SUPERSEDED
REJECTED
ACCEPTED
INVALIDATED
```

---

## 39. Recommendation Acceptance Offline

By default, important recommendation acceptance should require online authorization.

If an explicitly approved low-risk offline acceptance exists:

* it must be queued;
* authorization must be revalidated;
* resulting ERP operation must follow normal transaction rules;
* server must remain authoritative.

High-risk operations must remain server-required.

---

## 40. AI Assistant Offline

The AI assistant is generally server-required.

Offline mode may provide:

* previously generated answers;
* cached explanations;
* locally available static help.

The assistant must not imply that it can access current ERP data while offline.

---

## 41. Offline Assistant State

Example:

```text
AI Assistant

Offline

Current ERP information is unavailable.

You can view previous answers,
but new AI analysis requires connection.
```

This prevents users from mistaking cached content for current information.

---

## 42. AI Notifications Offline

AI notifications already synchronized to the device may remain visible.

New server-side AI notifications cannot be assumed available while offline.

When connectivity returns:

* missed notifications may synchronize;
* duplicate notifications must be prevented;
* notification authorization must be revalidated.

---

## 43. AI Job Synchronization

Long-running AI jobs are server-owned.

The frontend may store:

* local request UUID;
* server job UUID;
* local state;
* last known server state.

Example:

```text
Local Request
     ↓
Server Job
     ↓
RUNNING
     ↓
SUCCEEDED
```

The local device must not invent a successful job state.

---

## 44. Job Status Reconciliation

When reconnecting, the frontend must reconcile local state with the server.

Server state wins.

Example:

```text
Local:
RUNNING

Server:
FAILED

Result:
FAILED
```

The frontend must not retain `RUNNING` after reconciliation.

---

## 45. Duplicate Job Prevention

AI request synchronization must use operation UUID/idempotency.

If the same offline request is transmitted multiple times:

```text
Operation UUID X
      ↓
Request 1 → accepted
Request 2 → same operation
Request 3 → same operation
```

the server must not create multiple AI jobs when the operation is intended to be idempotent.

---

## 46. Payload Integrity

The server must validate the payload associated with an operation UUID.

If the same operation UUID is reused with a different payload:

```text
Operation UUID = X
Payload A → accepted

Operation UUID = X
Payload B → rejected
```

This prevents accidental or malicious request replacement.

---

## 47. Partial Synchronization

Synchronization may partially succeed.

Example:

```text
10 AI requests

8 synchronized
1 conflict
1 rejected
```

The frontend must preserve each request's individual state.

One failure must not roll back unrelated successfully synchronized requests.

---

## 48. Sync Retry

Retryable failures may enter:

```text
RETRY_PENDING
```

Retry must use bounded backoff.

The frontend must avoid infinite retry loops.

Permanent failures must move to:

```text
FAILED
```

or:

```text
REJECTED
```

according to the error classification.

---

## 49. Dead-Lettered AI Requests

Requests that cannot safely be retried may enter a dead-letter state.

Example causes:

* permanently invalid request;
* unsupported model;
* incompatible configuration;
* revoked permission;
* expired entitlement;
* invalid Business;
* corrupted local payload.

The user should receive a clear explanation where appropriate.

---

## 50. Conflict State

A conflict means the system cannot safely determine that the local operation should be applied automatically.

Examples:

* stale configuration;
* changed Business/Branch scope;
* model incompatibility;
* changed recommendation state.

The frontend must expose the conflict clearly.

---

## 51. Conflict Resolution

Conflict resolution must:

* identify the affected AI operation;
* preserve original local request;
* preserve server state;
* identify the reason;
* avoid silent overwrite;
* create a new request/version if the user retries;
* preserve audit context.

---

## 52. No Silent Last-Write-Wins

Important AI state must not use uncontrolled last-write-wins.

Especially:

* recommendations;
* approvals;
* configuration;
* AI-assisted actions;
* model-linked results.

Explicit conflict handling is preferred.

---

## 53. Offline Cache and Branch Switching

When Branch context changes while offline:

* only cached results for the new authorized Branch may be shown;
* unavailable Branch data must remain inaccessible;
* previous Branch results must not be relabeled;
* queued requests must retain their original Branch scope.

---

## 54. Device Trust

Offline AI functionality is available only to trusted devices according to the general device trust architecture.

A new/untrusted device cannot establish offline AI authority.

The device must first complete online registration and trust establishment.

---

## 55. Offline Authorization

Offline authorization must be:

* signed;
* time-bounded;
* associated with Business;
* associated with employee/device context;
* associated with permitted scope;
* revocable through server state when connectivity returns.

Offline authorization does not grant more permission than the server granted.

---

## 56. Offline Authorization Expiry

When offline authorization expires:

* new offline AI operations must stop;
* cached historical results may remain viewable if allowed;
* queued requests remain subject to later server validation;
* core ERP behavior follows the general Offline architecture.

The frontend must clearly distinguish authorization expiry from AI service failure.

---

## 57. Clock Rollback

Offline AI synchronization must account for device clock tampering.

The system should use:

* server timestamps;
* trusted synchronization timestamps;
* monotonic/local sequence information where appropriate;
* rollback detection.

Client time must not be treated as authoritative for security decisions.

---

## 58. Timestamp Integrity

Important AI records should retain:

* client-created timestamp;
* server-received timestamp;
* server-processed timestamp where applicable.

The server timestamp is authoritative for server-side lifecycle events.

---

## 59. Data Ordering

AI synchronization must preserve logical ordering where order matters.

For example:

```text
ERP transaction
     ↓
Inventory update
     ↓
AI input availability
     ↓
AI result
```

An AI result based on data that has not yet become authoritative must not be presented as current.

---

## 60. Sync Dependencies

AI synchronization may depend on:

* ERP transaction sync;
* configuration sync;
* authorization sync;
* subscription state;
* model availability.

The synchronization engine should understand these dependencies rather than blindly processing every queue entry.

---

## 61. AI Result Freshness After ERP Sync

After significant ERP synchronization:

* previously cached AI results may become stale;
* affected forecasts/recommendations may require invalidation;
* new AI processing may be scheduled.

The system should not automatically claim that an old result reflects the newly synchronized ERP state.

---

## 62. Example: Offline Sales

```text
Offline

Order A
Order B
Order C

        ↓ reconnect

ERP transaction synchronization

        ↓

Server validates orders

        ↓

Authoritative sales state updated

        ↓

AI forecast input refreshed

        ↓

New AI result generated

        ↓

Frontend receives updated forecast
```

The AI forecast must not be generated from an incomplete local state and then treated as authoritative.

---

## 63. Example: Offline Inventory

```text
Offline inventory transactions
        ↓
Synchronization
        ↓
Server inventory validation
        ↓
Authoritative stock
        ↓
AI stock-risk calculation
        ↓
Recommendation
```

The recommendation must use authoritative synchronized inventory state.

---

## 64. Example: Offline Price Configuration

A price configuration change created elsewhere while the POS device is offline must not silently overwrite the local transaction price.

```text
Offline Order
Price Version A
        ↓
Order synchronized
        ↓
Price Version B synchronized
```

The Order retains Price Version A according to the existing price snapshot rules.

---

## 65. Example: Offline Recommendation

```text
AI Recommendation R1
Generated:
10:00

User goes offline

Recommendation remains visible

Server data changes

Device reconnects

R1 marked stale/superseded
```

The frontend must not continue presenting R1 as a fresh recommendation.

---

## 66. Synchronization and Historical Integrity

Synchronization must never rewrite historical ERP transactions because of a newer AI result.

AI results may explain or predict ERP data.

They must not reinterpret:

* historical order price;
* payment;
* refund;
* inventory transaction;
* cash session;
* payroll;
* report snapshot.

---

## 67. AI and Report Synchronization

AI explanations associated with reports must preserve the report version they were based on.

Example:

```text
Report Version 12
      ↓
AI Explanation E1
```

If the report becomes Version 13:

```text
Report Version 13
      ↓
New AI Explanation E2
```

E1 remains associated with Version 12.

---

## 68. AI and Configuration Synchronization

When a configuration change becomes effective:

* cached incompatible AI results may be invalidated;
* new requests use the new configuration;
* historical results remain identifiable by their original configuration.

Configuration synchronization must not rewrite historical AI lineage.

---

## 69. AI and Model Synchronization

The device must not automatically install an arbitrary model received from the network.

Any local model must come from an approved deployment process.

Model synchronization requires:

* model identity;
* version;
* checksum;
* compatibility;
* approval state;
* deployment authorization.

---

## 70. Model Rollback

If a model is rolled back on the server:

* new AI requests use the newly active approved model;
* existing completed results remain historical;
* cached results may remain visible if still valid;
* model metadata must remain associated with each result.

---

## 71. Provider Failure During Synchronization

If an external AI provider is unavailable:

* ERP transactions continue;
* queued AI jobs remain queued/retryable where appropriate;
* the frontend shows AI service unavailability;
* no false success is displayed.

---

## 72. Synchronization Security

AI synchronization must validate:

* authenticated device;
* employee context;
* Business;
* Branch;
* operation UUID;
* payload integrity;
* authorization;
* subscription;
* configuration;
* request signature where applicable.

Untrusted synchronization payloads must be rejected.

---

## 73. Synchronization Encryption

AI synchronization traffic must use the same secure transport requirements as the rest of the ERP.

Sensitive local AI data must be encrypted at rest according to the frontend offline storage architecture.

---

## 74. Sensitive AI Data

Offline storage should minimize sensitive data.

The device should not persist unnecessary:

* personal information;
* employee information;
* customer information;
* detailed financial information;
* prompts containing sensitive data;
* full LLM conversations.

Retention should be purpose-driven.

---

## 75. AI Conversation Cache

If AI assistant conversations are cached:

* they must be scoped to the authorized user/context;
* retention must be limited;
* sensitive content should be minimized;
* conversations must not be shared between Business contexts;
* server synchronization must preserve authorization.

---

## 76. Conversation Synchronization

A conversation created online and later viewed offline should retain:

* conversation UUID;
* message sequence;
* timestamp;
* scope;
* assistant/model version where relevant.

New messages generally require online AI execution.

---

## 77. Offline Feedback

User feedback on cached AI results may be queued.

Example:

```text
Recommendation R1
      ↓
User: Not helpful
      ↓
Offline feedback queued
      ↓
Reconnect
      ↓
Server validates context
      ↓
Feedback stored
```

Feedback must not automatically change the recommendation or ERP state.

---

## 78. AI Export Offline

Previously synchronized AI results may be exportable offline only if:

* the data is authorized;
* export functionality is explicitly supported offline;
* local data is sufficient;
* export does not require server-side fresh data.

The export must be clearly identified as based on the cached result.

---

## 79. Offline AI Audit

Offline actions requiring audit should preserve:

* operation UUID;
* employee UUID;
* device UUID;
* Business UUID;
* Branch UUID;
* local timestamp;
* synchronization timestamp;
* server result;
* operation status.

The server remains authoritative for the final audit event.

---

## 80. Synchronization Observability

The system should monitor:

* AI sync queue size;
* pending requests;
* retry count;
* conflict count;
* rejected requests;
* expired requests;
* stale results;
* synchronization latency;
* provider failures;
* model mismatch;
* configuration mismatch.

Operational monitoring belongs to the AI Operations architecture.

---

## 81. User Sync Status

The frontend should provide understandable synchronization status.

Example:

```text
AI
● Synced
```

```text
AI
◐ 2 requests pending
```

```text
AI
! 1 request requires attention
```

Technical queue internals should not overwhelm ordinary users.

---

## 82. Sync Conflict UX

Example:

```text
AI recommendation could not be synchronized.

Reason:
The Branch configuration changed before
the request reached the server.

[View]
[Generate Again]
```

The original request remains traceable.

---

## 83. Retry UX

The user may retry when appropriate.

Retry should:

* create a new operation where required;
* preserve the original failed operation;
* use current authorized context;
* use current configuration;
* avoid duplicate execution.

---

## 84. Synchronization Recovery

After unexpected device shutdown:

* durable local queue entries must be recoverable;
* completed requests must not be duplicated;
* partially synchronized operations must be reconciled with server state;
* invalid local state must be discarded or marked failed.

---

## 85. Device Replacement

If a trusted device is replaced:

* local AI cache is not automatically transferred;
* new device must complete trust registration;
* server-synchronized AI results may be downloaded again if authorized;
* pending local operations on the old device remain tied to the old operation/device context.

---

## 86. Revoked Device

If a device is revoked:

* new offline AI operations stop;
* synchronization from the revoked device must be rejected;
* cached data may be invalidated according to security policy;
* queued operations require explicit server handling.

A revoked device must not regain trust merely by reconnecting.

---

## 87. Subscription Expiry While Offline

If the device goes offline while subscription is active:

* offline authorization remains bounded by the existing offline authorization policy;
* the device must not assume indefinite entitlement;
* upon reconnect, current subscription state is authoritative;
* queued AI operations are revalidated.

---

## 88. Business Deletion While Offline

If Business deletion occurs while a device remains offline:

* the device cannot preserve the Business indefinitely;
* upon reconnection, server lifecycle state is authoritative;
* queued AI operations are rejected;
* cached data follows deletion/retention policy;
* synchronization must not recreate deleted records.

---

## 89. Stale Data Warning

Warnings should be proportional to risk.

For example:

```text
Low-risk historical insight
→ "Generated yesterday"
```

versus:

```text
Operational recommendation
→ "Outdated — refresh required"
```

The UI must not unnecessarily block harmless historical viewing.

---

## 90. AI Sync Priority

Synchronization priority should generally follow:

1. Core ERP transactions
2. Security and authorization state
3. Business/Branch configuration
4. AI requests affecting current operations
5. AI results
6. AI feedback
7. Non-critical AI telemetry

This prevents AI work from competing with critical ERP synchronization.

---

## 91. Resource Limits

Offline AI queues must be bounded.

The system should define limits for:

* maximum queued requests;
* maximum local AI cache size;
* maximum conversation storage;
* maximum retry count;
* maximum synchronization batch;
* maximum payload size.

When limits are reached, the system must fail predictably.

---

## 92. Queue Overflow

If the local AI queue reaches its limit:

```text
AI request cannot be queued offline.

Connect to the server to continue.
```

The frontend must not silently discard a request that the user believes was accepted.

---

## 93. Payload Size

Large AI payloads should not be stored or synchronized unnecessarily.

The frontend should prefer:

* references to server data;
* structured identifiers;
* bounded text;
* bounded history.

The Backend retrieves authoritative data after authorization.

---

## 94. Sync Batch

AI synchronization should use bounded batches.

The batch size should be configurable according to the general synchronization architecture.

Large AI payloads must not block normal ERP synchronization.

---

## 95. AI Sync and Core ERP Continuity

AI synchronization must run independently from critical ERP operations.

If AI synchronization is delayed:

* orders continue;
* payments continue;
* inventory operations continue;
* cash sessions continue;
* attendance continues;
* normal ERP synchronization continues.

---

## 96. AI Sync Failure Recovery

AI synchronization failure must support:

* retry;
* backoff;
* conflict state;
* dead-letter state;
* user-visible recovery;
* server reconciliation.

AI synchronization failure must not require database rollback of already committed ERP transactions.

---

## 97. Data Consistency Rule

The system must maintain:

```text
ERP consistency
>
AI consistency
>
AI freshness
```

In other words:

1. Authoritative ERP correctness is highest priority.
2. AI result consistency is next.
3. Immediate AI freshness is lower priority than correctness.

---

The following baseline targets apply:

| Operation                            |                              Target |
| ------------------------------------ | ----------------------------------: |
| Offline AI queue write               |                        p95 ≤ 100 ms |
| Local AI cache read                  |                        p95 ≤ 100 ms |
| AI sync request acceptance           |                           p95 ≤ 1 s |
| AI job reconciliation                |                           p95 ≤ 1 s |
| AI result synchronization            | p95 ≤ 2 s after server availability |
| Sync conflict detection              |                        p95 ≤ 500 ms |
| Local sync status update             |                        p95 ≤ 200 ms |
| AI synchronization availability      |                             ≥ 99.5% |
| Duplicate AI job creation from retry |                                   0 |
| Unauthorized AI data synchronization |                                   0 |
| Business/Branch cross-scope leakage  |                                   0 |

These are AI-specific targets and complement the general Offline and Synchronization SLOs.

| Model version changed       | Apply deterministic compatibility policy         |
